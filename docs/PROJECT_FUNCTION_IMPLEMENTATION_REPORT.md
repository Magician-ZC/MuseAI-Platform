## 1. 结论摘要

MuseAI 目前不是一个单一形态的应用，而是两条产品线共用一个叙事技术底座：

1. **本地 AI 创作/陪伴产品**：React + Tauri，包含作品管理、写作、设定、角色、聊天、冒险、故事导演、关系沉淀、移动端局域网访问等功能。
2. **云端多人世界平台**：玩家端 + Rust/Axum 后端 + 管理后台，覆盖世界与角色资产、多人世界房间、剧情事件、成长、经济、风控、运营、直播/竞技场等广泛领域。

当前总体判断：

| 维度 | 判断 | 说明 |
|---|---|---|
| 本地端功能实现 | **较完整** | 核心页面、Tauri 命令、数据持久化和 AI 工作流均有实现及测试 |
| 共享叙事引擎 | **较成熟** | 角色/世界提取、导演制叙事、状态机、约束、回放与分支均有系统实现 |
| 平台后端领域覆盖 | **很广，代码实现度高** | 全特性测试通过，但不少能力默认受功能开关控制 |
| 平台玩家端闭环 | **较完整但受控开放** | 大厅、房间、资产、背包、羁绊、报告、钱包及“我的旅程”九类能力均有玩家界面；部分能力仍受 feature flag 与生产配置限制 |
| 运营管理端 | **主要业务台已实现** | 九大业务模块可用；部分全局导航控件与监控字段仍是预览或静态占位 |
| 生产就绪度 | **不足** | 短信、实名、支付、TTS、对象存储、任务队列等仍使用 Dev/本地实现或缺少真实供应商闭环 |
| 用户与商业验证 | **尚未完成** | 未见真实用户灰度、留存、付费、审核 SLA 或规模化运行数据 |

因此，本项目可定义为：**工程能力和领域模型已经达到大型可运行原型/内部 Alpha 水平，本地产品更接近可用；云平台仍不能宣称生产发布完成。**

## 2. 状态口径

本报告使用以下五级标记：

| 标记 | 含义 |
|---|---|
| **已验证** | 本次盘点实际执行测试、构建或运行时冒烟并通过 |
| **已实现** | 代码、路由、状态与测试存在，但本次未做完整真实用户端到端验证 |
| **受控开放** | 已实现，但默认关闭、按功能开关/角色/世界范围开放，或只提供 API |
| **Dev/占位** | 接口形态存在，但默认实现是开发桩、本地替代或预览数据 |
| **未闭环** | 规格中存在，或上下游部分存在，但缺少完整生产链路 |

### 7.2 平台内部治理能力

后端还实现了运行时组装、准入、安全、功能开关、SLO、降级、错峰、录制等内部模块：

- 容器/世界运行时组装与准入；
- 词典筛查、语义复检接口、安全扫描与处置；

- 运行记录和重放；
- 管理侧安全重检和批量扫描接口。

功能开关**全部已接入解析链路**（`wired: true`），且仅 `MUSE_SAFETY_LEXICON` 默认开启、其他新增玩法与治理功能一律默认关闭——后者由红线用例 `red_line_only_safety_chain_defaults_on` 锁死，任何人把某个未验证功能的默认值改成 `true`，测试立刻红。实现存在并不代表普通用户默认可见。⚠️ **开关个数本文不复述**（盘点当日是 18 条，此后每批开发都会让它过期）：清单与默认值以 `server/src/flags/mod.rs` 的 `KNOWN_FLAGS` 为准。

### 7.3 数据与迁移

- 支持 SQLite 和 PostgreSQL，当前共有约 **50 个迁移文件**；
- 默认开发配置为内存 SQLite；
- Docker Compose 提供 PostgreSQL 与 Redis；
- ⚠️ **本条已订正（2026-07-29）**：盘点当日只实测了 SQLite 启动链路。此后 2026-07-27/28 已在真实 PostgreSQL 16 上跑过全量两个 feature 组合、零失败且与 SQLite 逐条同数（两条根因——`Any` 驱动不改写 `?` 占位符、PG 的 `SUM()` 返回 `numeric`——均已修完，见 VALIDATION §3 与 §3.57）。**但那只证明 SQL 可移植**：连接池、超时、迁移锁、故障恢复仍零验证，按状态语言是 `Implemented` 而非 `Production-ready`；
- Redis 当前未真正接入应用队列，服务端使用 `MemQueue`。

管理端存在以下体验与完整性问题：

- 顶部全局搜索没有实际查询动作；
- 通知按钮只有预览徽标，没有接入真实未读计数；

- 校准页面部分文案与当前后端实现有漂移，不能把页面说明当作最新引擎事实。

因此管理端适合内部运营试用，但还需要一次专门的“所有按钮可达性 + 数据语义 + 权限矩阵”人工验收。

## 11. 主要风险与优先级

### P0：上线前必须解决

1. **替换所有 Dev Provider**：真实短信、可信身份/年龄核验、内容与图片审核、支付、TTS。
2. **生产持久化**：PostgreSQL 迁移与备份恢复实证；Redis/持久队列真正接入；生产对象存储和 CDN。
3. **安全与合规**：强 JWT、受限 CORS、Tauri CSP、密钥轮换、未成年人保护、数据删除/导出和审计闭环。
4. **经济与资金安全**：订单幂等、回调验签、退款、对账、结算、提现和财务审计。
5. **明确首发范围**：决定首发是本地创作产品、云世界平台，还是有明确连接方式的双产品；不能把默认关闭/API-only 功能写成已发布。

### P1：Alpha/Beta 闭环

1. 在开启对应 feature flag 的联调环境完成 Onboarding、邀请、OOC、IFLine、子剧情、纪念堂、社交解锁、章节和 Live Stage 的真实账号/多用户 E2E；玩家端页面与 API 接线已补齐。
2. 增加浏览器 E2E、Tauri E2E、多用户房间、WebSocket 断线重连和管理权限矩阵测试。
3. 清理管理端静态按钮、预览字段、TODO 和过期文案。
4. ~~拆分前端和管理端大包，按路由懒加载~~ —— **2026-07-29 已做**（两端入口各降 ~67-77%，见 §10.1）。剩下的是「建立首屏与弱网性能门槛」：**尚无门槛值、也无自动化度量**，包体变大不会让任何检查变红。
5. 建立文档状态单一来源，避免 `VALIDATION.md` 旧结论与后续修订并存。

### P2：规模化运营

1. 真实模型下的角色一致性、剧情安全和回放差异基准；
2. 容量、成本、模型降级、SLO、告警和错峰效果的实测；
3. 世界冷启动、创作者供给、用户留存、安全申诉和运营响应指标；
4. 竞技场、直播、礼物与剧情的全链路灰度；
5. 桌面签名、公证、自动更新和跨平台兼容矩阵。

## 12. 建议发布顺序

| 阶段 | 目标 | 验收门槛 |
|---|---|---|
| T0：范围冻结 | 明确本地端与云平台首发边界；冻结默认开启功能 | 产品、路由、开关、文档四者一致 |
| T1：本地内测 | 先验证创作、聊天、冒险、故事和本地数据安全 | 真实模型 E2E、桌面安装包、恢复与导出通过 |
| T2：平台技术 Alpha | 小规模受控账号、单世界、多用户房间 | PG/队列/对象存储、审核、日志、告警、压测通过 |
| T3：运营 Alpha | 审核、风控、工单、经济全部可操作 | 权限矩阵、申诉 SLA、对账和演练通过 |
| T4：封闭 Beta | 接入真实供应商与支付，逐步启用功能开关 | 真实用户留存、安全率、成本与稳定性达标 |
| T5：公开发布 | 只发布已闭环功能 | 合规、灾备、资金、客服、监控与发布回滚全部验收 |

## 13. 最终判定

### 可以确认的事实

- 项目已经具备覆盖创作、角色、世界、叙事、多人平台、运营治理和商业扩展的完整代码骨架；
- 核心功能不是只有页面或文档，前端、Rust 引擎、Tauri 与平台后端都有大量实现和自动化测试；
- 当前全特性测试与生产构建基线健康，本地 Dev 鉴权链路可运行；
- 平台后端的功能范围明显大于当前玩家端实际可用范围。

### 不能据此宣称的事项

- 不能宣称真实短信、实名、支付、审核、TTS、对象存储和任务队列已经生产可用；
- 不能把默认关闭、API-only、预览字段或 Dev Provider 描述为用户已获得的正式能力；
- 不能用“全部套件通过”替代真实桌面、浏览器、多用户、供应商、生产数据库和商业运营验证；
- 不能在没有灰度指标前宣称产品市场验证或商业模式成立。

综合看，下一步不应继续横向增加模块，而应以 **首发范围收敛、真实依赖替换、玩家/运营闭环和生产实证** 为主线，把现有庞大的实现面转化为可交付、可运营、可审计的产品。
